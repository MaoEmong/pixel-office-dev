# 회의를 거치는 작업 흐름 (T54)

## 사용자 흐름

부장과 대화 → 목표·범위·완료 기준 구체화 → 사용자가 작업 시작 → 부장이 필요한 팀장과 전문가 소집 →
의견 제출 → 상호 검토 → 부장 회의록·팀별 계획 확정 → 업무 실행 → 부장 최종 보고 → 사용자 검수 완료.
기존 빠른 지시는 유지하되, 진행 중인 계획·회의를 우회하여 구현을 시작할 수 없다.

## 상태와 계약

- 상태: clarifying, meeting, executing, review, completed, blocked, cancelled.
- 회의 상태: collecting(1차), reviewing(2차), deciding(부장 결정).
- MCP: meeting_open(부장, 같은 부서의 살아 있는 참석자), meeting_speak(초대된 참석자, 해당 차례의 의견 한 건),
  meeting_decide(부장, 회의록·팀장별 업무·완료 기준·의존 팀장 ID).
- 두 차례 모든 참석자의 발언이 모여야 결정할 수 있다. 부서는 회의 하나만 활성화할 수 있다.
- 임의의 부서·참석자·팀원에게 실행 업무를 배정할 수 없다. 의존성 순환·중복 담당·빈 계획을 거부한다.
- 회의 업무는 일반 구현 task가 아니다. 실행 확정 전 delegate와 파일 변경·쓰기 셸 도구를 차단한다.
- 계획 확정 후 기존 delegate/report 사슬을 사용한다. 의존 업무는 선행 업무가 done일 때 배정한다.
- 완료 보고는 검수 단계로 보내며, 사용자 검수 완료가 작업 완료다. 중단·오류는 기록을 보존한다.
- 작업안, 발언, 회의록, 계획, 결과를 SQLite에 저장하고 프로젝트 .pixel-office/workflows에도 기록한다.
- 재접속 시 최신 기록을 다시 읽는다. 재시작 후 회의 재개는 미제출 의견만 다시 요청한다.

## 검증 기준

대화 단계 구현 차단, 두 차례 의견과 상호 검토, 참석자·직급 검사, 계획 검증, 의존 업무 실행,
보고→검수 전환, 취소와 오류, 회의 복구, 기존 빠른 지시와의 호환, 화면 클릭 실기.
