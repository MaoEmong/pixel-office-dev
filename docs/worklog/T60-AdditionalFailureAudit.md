# T60 — 추가 예측 실패 점검

2026-10-14, 941ad93 기준. 이번 단계는 점검이며 구현 코드는 변경하지 않았다.
실제 사용자 데이터와 CLI 인증을 건드리지 않고 임시 데이터·가짜 PTY·전송 실패 주입으로 확인했다.

아래 재현된 다섯 항목은 후속 [T61 수정·검증](T61-FailureRecoveryAndErrorPanels.md)에서 처리했다.
이 문서는 수정 전 점검 기록이다.

## 재현된 문제와 보호 장치 공백

1. **우선: 작업 시작 부분 실패로 흐름이 멈춤.** Coordinator.start는 meeting 상태를 먼저 저장한 뒤
   startTask를 호출한다. 작업 생성 실패를 주입하면 meeting 상태와 rootTaskId 없음이 남는다.
   같은 start 요청을 재시도하면 clarifying 단계가 아니라는 오류가 난다.
   실패 시 상태 복원 또는 전달 대기 상태·재시도 경로가 필요하다.
   근거: dev/daemon/src/workflow/Coordinator.ts start.

2. **우선: 이동된 프로젝트의 빈 경로를 재생성.** 프로젝트 폴더를 이동한 뒤 기존 멤버를 restart했다.
   ensureProjectDataDir의 recursive mkdir가 원래 경로를 다시 만들고 가짜 PTY 재시작은 성공했다.
   새 경로에는 프로젝트 파일이 없고 이동한 경로에만 원본 파일이 있었다.
   실제 CLI의 모델 작업은 실행하지 않았다. 재시작·복구 시 기존 cwd 존재 여부·디렉터리 여부를 먼저 검사하고
   폴더 재지정 흐름을 제공해야 한다. 프로젝트 폴더 자체를 자동 재생성하면 안 된다.
   근거: dev/daemon/src/pty/projectSessions.ts ensureProjectDataDir, Office.spawnMember.

3. **실패한 대화 전송이 저장되고 재시도 시 중복.** Coordinator.discuss의 host.send 실패를 주입했다.
   호출은 오류로 끝나지만 사용자 메시지는 저장됐다. 같은 내용을 다시 요청하면 메시지가 두 개가 된다.
   전달 상태 표시 및 요청 식별자를 통한 중복 방지, 실패한 메시지 재전송이 필요하다.
   근거: dev/daemon/src/workflow/Coordinator.ts discuss.

4. **준비 시간 초과 뒤 starting 상태 유지.** Codex 가짜 빈 화면 세션에서 시계를 181초 진행했다.
   준비 화면에 도달하지 못했다는 알림은 발생하지만 상태는 starting이며 감시 타이머는 종료됐다.
   오류 또는 조치 대기 상태로 전환하고 로그인·화면 변경·재시작 안내를 제공해야 한다.
   근거: Office.watchBootReady. 실제 CLI 로그인 만료를 재현한 것은 아니다.

5. **일반 생성의 전체 동시 세션 상한 없음.** 한 부서에서 팀 15개를 생성했으며
   부장 포함 가짜 세션 16개가 동시에 살아 있었다. 팀 정원과 재시작 복구의 동시 부팅 제한은 있지만
   일반 생성의 전체 세션·부서 팀 수 제한은 아니다. 사용자 지정 상한과 대기·거부 안내가 필요하다.
   메모리·실제 비용 소모는 측정하지 않았다. 결함이라기보다 과도한 자원 사용 방지 장치의 공백이다.
   근거: Office.createTeam, spawnNewMember.

재현 스크립트: 로컬 .local/t60-audit.mts, .local/t60-boot.mts. assertion 모두 통과.

## 코드에서 추가로 남은 확인 범위

- submitLost는 알림을 보내지만 이미 assigned로 기록된 작업을 별도 전달 실패 상태로 바꾸지는 않는다.
  제출 실패와 실제 모델 작업 중을 구분하는 상태 및 중복 없이 재전송하는 경로를 점검해야 한다.
- 앱 RPC는 15초 뒤 시간 초과를 반환하지만 서버 작업 취소·요청 중복 방지는 일반 RPC에 적용되지 않는다.
  늦은 성공 뒤 사용자가 재요청할 때 중복 실행되는지는 메서드별로 실패 주입 검사가 필요하다.
- 작업 도중 인증 만료·사용량 제한·서비스 장애와 최신 CLI 화면 변화는 아직 실제 서비스 실패를 재현하지 않았다.
  기존 모델 전환 화면 처리와 알림은 있으므로 모든 한도 오류가 무처리라고 단정하지 않는다.
- 실제 디스크 전체 고갈·DB 쓰기 실패·저장 중 강제 종료의 정합성은 별도 격리 검사가 필요하다.

권장 순서: 작업 흐름 부분 실패·중복 요청 → 프로젝트 경로 보호 → CLI 준비 실패 상태 → 세션 상한.
