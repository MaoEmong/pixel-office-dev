# T54g — GUI 직접 조작 검증

최종 Windows release 앱을 직접 실행해 두 작업을 검사했다.

1. 부장과 대화 → 작업 시작·회의 소집 → Claude 팀장 2명 생성.
2. 1차 제안 2건, 2차 상호 검토 2건, 부장 결정과 회의록 표시.
3. 작성팀장 배정됨 / 검토팀장 선행 업무 대기, 완료 기준·선행 담당 표시.
4. 회의 화면을 닫고 기존 내 책상 Write 카드의 허가 버튼을 직접 클릭.
5. 작성 완료 뒤 검토 배정, 두 팀 완료, 부장 최종 보고 전문을 스크롤해 확인.
6. 검수 완료 버튼을 클릭해 완료 상태 확인.

첫 결과: sandbox/gui-meeting.txt = GUI_MEETING_OK.
둘째 결과: 하단 대화 입력 Enter로 gui-recovery 작업안을 보냄 → 명시적 회의 시작.
회의가 진행되는 동안 앱 정상 종료를 요청했고 닫기 확인 시점에는 계획이 확정돼
실행 단계로 넘어가 있었다. 재실행 후 같은 작업안·4개 발언·계획이 유지됐고,
복원된 Write 허가를 클릭해 이어서 작성·검토·최종 보고·검수를 완료했다.
sandbox/gui-recovery.txt = GUI_RECOVERY_OK. 앱 재시작 전에는 파일이 없었고
새 구현 task나 중복 Write 없이 기존 task를 이어갔다.
팀 해산 뒤에도 참석자·업무 담당·선행 담당 이름이 유지됨을 GUI에서 확인했다.

회의 중 구현 조기 실행은 hook/Office 자동 검사가, 누락 의견만 재요청하는
회의 재개는 Coordinator 테스트가 검사한다. GUI 재시작 실기는 실행 단계 복구다.
Windows release 빌드, Flutter analyze, 위젯 전체 검사는 T54e 참고.
최종 앱은 실행 상태로 남긴다.
