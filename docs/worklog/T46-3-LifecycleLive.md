## 고친 결함

### ① `suspended` 를 hook 이 덮어 "어제의 사무실" 이 통째로 죽어 있었다 — `39700a2`

**증상.** 2번을 처음 돌렸을 때 로그는 `3명 잠시 닫힘(suspended)` 인데 DB 를 열어 보니 셋 다 `exited` 였다.
3번(다시 켜기)에서 아무도 돌아오지 않고 부서가 `팀 개발 · 전원 퇴근` 으로 열렸다 —
D-47 §5 가 없애려던 **T41 의 옛 고통 그대로**다. `img/T46-3-defect1-no-recovery.png`

**원인.** `Office.shutdown()` 이 `suspendLiveMembers()` 로 `suspended` 를 적은 **뒤에** 정중한 종료(`/exit`)가
돌고, 진짜 Claude 는 죽기 직전 `SessionEnd{reason:'prompt_input_exit'}` hook 을 **한 번 더** 보낸다.
`BaseHooksAdapter.onSessionEnd` 가 그걸 받아 status 를 `exited` 로 되돌렸다. 이벤트 표에 그대로 찍혀 있다:

```
#1220 14:37:53.291 m_4d513a…  idle {"summary":"session ended: prompt_input_exit"}
#1221 14:37:53.298 m_df2f4a…  idle {"summary":"session ended: prompt_input_exit"}
#1222 14:37:53.308 m_bebe35…  idle {"summary":"session ended: prompt_input_exit"}
```

`Office.onPtyExit` 에는 `exitMode === 'shutdown'` 가드가 있었지만 **hook 경로에는 그 가드가 없었다.**

**고침.** `BaseHooksAdapter.setStatus` 가 현재 status 가 `suspended` 면 아무것도 하지 않는다(늦게 오는 `Stop`
→ idle 도 같이 막힌다). 되살릴 때는 Office 가 `spawnMember` 에서 먼저 `starting` 으로 바꾸므로 안 걸린다.

**테스트.** `ClaudeHooksAdapter.test.ts` +1, `Lifecycle.test.ts` +1(`FakePty.beforeExit` 훅을 더해 "CLI 가
죽기 직전" 을 재현 → suspended 유지 → 다음 기동이 말없이 복구).

### ② 데몬이 떴는데도 앱이 backoff 를 다 기다렸다 — `b961bf6`

`daemon.json` 이 +3.8초에 나오는데 앱은 +8.0초에야 붙었다. `RpcClient` 의 재접속 루프(1→2→4→5초)를
**아무도 깨우지 않았다** — T46-1(데몬)과 T46-2(앱 감시자) 사이에 배선이 없던 자리다.
`LifecycleGate` 가 감시자 상태를 듣다가 `running` 으로 **들어가는 순간** `retryNow()` 를 부른다.
첫 기동과 §4 재시작이 같은 길을 지난다. → **+4.2초**(데몬 준비 0.35초 뒤).

### ③ 앱을 강제 종료하면 데몬이 굳어 CLI 가 영원히 남았다 — `9bc2117` (가장 심각)

**증상.** 5번에서 앱을 `taskkill /F` 했더니 **2분 30초 뒤에도** 데몬이 살아 있었다(CPU 100%),
`claude.exe` 3개 + 확인용 세션 2개도 그대로, `daemon.json` 도 안 지워졌다. **로그에는 아무것도 안 남았다.**

**원인은 수명 주기가 아니라 파이프였다.** 앱은 데몬을 파이프 모드로 띄운다(콘솔 창이 안 뜨는 유일한 모드,
T46-2 실측). 그 파이프를 읽는 사람은 앱 하나뿐이다. 앱이 죽으면 읽는 쪽이 사라지고, 그 뒤 데몬이
`console.log` 를 **한 줄만 써도**: ⓐ 그 write 가 영영 안 끝나고 ⓑ **이벤트 루프가 그 자리에서 멎고**
ⓒ 프로세스는 죽지도 않는다.

두 실험으로 못을 박았다.

```
(가) 같은 데몬을 콘솔에서(PIXEL_PARENT_PID 만 주고) 띄우고 그 부모를 죽였다
     [office] 부모 앱이 사라졌다 (pid 1428) — 사무실을 정리하고 데몬을 종료합니다
     [office] 종료: 세션 5개 닫음, 3명 잠시 닫힘(suspended)
     → 8개 전부 3.0초 만에 사라지고 daemon.json 삭제(+2.96초).  수명 주기 코드는 멀쩡했다.

(나) 파이프 부모/자식 둘만 두고 부모를 죽였다(임시 스크립트)
     t=2845ms ticks=26   ← 부모 살아 있음
     t=2956ms ticks=27
     t=3065ms ticks=28   ← 여기서 부모 사망. **그 뒤로 한 줄도 안 늘어난다**
     8초 뒤에도 자식은 살아 있음(종료도 진행도 없음)
```

**고침 — 앱이 띄운 데몬은 stdout 을 아예 쓰지 않는다.**
`dev/daemon/src/log.ts`(신규)가 `PIXEL_DAEMON_LOG` 이 있으면 `console.*` 를 그 파일에 **직접** 이어 쓴다
(`src/index.ts` 첫 줄 `installFileLog()`). 앱은 스폰 환경변수에 `PIXEL_DAEMON_LOG=<데이터 폴더>\daemon.log`
를 넣는다. 파이프는 계속 읽는다 — node·tsx 의 **네이티브 크래시**는 console 을 안 거치고 fd 로 나오기 때문이다.

덤: **앱이 죽은 뒤의 로그가 남는다.** 예전에는 `부모 앱이 사라졌다` 가 죽은 파이프로 흘러가 사고 원인을
볼 길이 없었다. 재검증에서 그 줄이 `daemon.log` 에 그대로 들어왔다.

**테스트.** `test/log.test.ts`(신규 5건) — 포맷·sink·설치/미설치 + **win32 실측 재현**: 진짜 자식의 파이프
읽는 쪽을 없애도 이벤트 루프가 계속 돌고 스스로 끝나며 끊긴 뒤의 줄도 파일에 남는다.
앱 쪽 `daemon_process_test.dart` +1(환경변수 전달).

### ④ 1분에 3번 죽여도 crash-loop 이 발화하지 않았다 — `b879442`

**증상.** 6번에서 `데몬이 반복해서 종료됩니다` 가 끝내 안 떴고, 세 번째 죽음 **36초 뒤에 네 번째 데몬이 떴다.**

**원인 둘.**
1. **붙기 전에 죽은 데몬은 죽음으로 세어지지 않았다.** `_watchChild` 는 `daemon.json` 이 보여 "붙었다" 가 된
   **뒤에야** 달린다. 실기에서 죽인 순간은 늘 "막 띄워서 아직 못 붙은" 때였다(+1.5초, +11.9초) — 그래서
   그냥 "못 붙었다" 로 처리되고 `_deaths` 는 1 그대로였다. **띄우자마자 죽는 것이야말로 crash-loop 의 본모습**인데,
   그 규칙이 가장 필요한 경우에 발화하지 않았다.
2. **포기해도 앞서 돌던 재시작 일정이 그것을 덮었다.** `_restartLoop` 는 `_stopped` 만 봤기 때문에
   `_fail(crashLoop)` 뒤에도 다음 칸에서 `restarting` 을 다시 emit 하고 데몬을 또 띄웠다.

**고침.** `_spawnOnce` 가 스폰 직후부터 `exitCode` 를 지켜보다 붙기 전에 죽으면 `_countDeath`
(`killTree()` 가 exitCode 를 채우므로 **치우기 전에** 판정한다 — 안 그러면 "못 떴다" 까지 죽음이 된다).
그리고 `_abandoned` 깃발을 두어 `_restartLoop`·`_spawnOnce`·`_onDeath`·`_waitReachable` 이 같이 보고,
`다시 시도` 만 그것을 푼다.

### ⑤ "앱을 닫아도 계속 일하기" 가 정반대로 동작했다 — `373b2e6`

설정을 켜고(파일에 `{"keepDaemonOnExit":true}` 확인) 창을 닫았더니 **데몬도 세션도 전부 꺼졌다.**

```
[office] 부모 앱이 사라졌다 (pid 16500) — 사무실을 정리하고 데몬을 종료합니다
[office] 종료: 세션 5개 닫음, 3명 잠시 닫힘(suspended)
```

앱 쪽은 설계대로 아무것도 안 했다. 문제는 **데몬 쪽**이다 — 이 설정은 `main()` 이 `PIXEL_PARENT_PID` 를
넘길지만 정하는데, 앱을 **켠 뒤에** 켜면 데몬은 이미 그 pid 를 들고 기동한 뒤다. 그리고
`hello{parentPid}` 는 대상을 **바꿀** 수만 있고 **끌** 수는 없었다.

**고침.** 끄는 말을 하나 만들었다(멱등): `daemon.stopWatchingParent` → `{stopped: boolean}`.
`AppExitCoordinator` 가 "계속 일하기" 로 빠져나가기 **전에** 한 번 부른다(실패해도 종료는 안 막는다).
PROTOCOL.md 의 메서드 표·"수명 주기" 절·와이어 요약에 넣었다.

### (+) 알려진 구멍을 닫았다 — `e11a08e`

"다시 출근한 뒤에 고용하세요" 라고 말한다.

## 발견한 함정

1. **윈도우에서 "읽는 쪽이 사라진 파이프" 는 프로세스를 죽이지 않고 멈춘다.** EPIPE 예외도, 종료도 아니다 —
   `console.log` 한 줄에 이벤트 루프가 그대로 선다. GUI 앱이 콘솔 자식을 파이프로 띄우는 구조라면
   **자식이 부모보다 오래 살 수 있는 모든 경로**를 이 눈으로 다시 봐야 한다(T46-2 함정 1 의 뒷면이다:
   "파이프를 누가 읽어야 한다" 는 맞았고, **그 누가 죽으면 어떻게 되는지**가 빠져 있었다).
2. **"정중한 종료" 는 hook 을 한 번 더 부른다.** `/exit` 는 조용히 끝나지 않는다 — CLI 는 죽기 직전
   `SessionEnd` 를 보낸다. 종료 절차가 DB 에 적어 둔 상태는 **그 뒤에 도착하는 hook 으로부터도** 지켜야 한다.
   가짜 pty 로는 이 순간이 존재하지 않는다(그래서 `FakePty.beforeExit` 를 만들었다).
3. **"죽었다" 를 세는 자리가 하나면 모자란다.** 감시자는 "붙은 자식" 의 죽음만 셌는데, crash-loop 은
   보통 **붙기 전에** 죽는다. 재시도 카운터를 만들 때는 *성공한 적 없는 시도*가 어디로 새는지 봐야 한다.
4. **설정을 "기동 때 한 번" 읽는 값으로 쓰면 런타임 토글이 거짓말이 된다.** ⑤는 설정이 앱 쪽 분기만
   바꾸고 이미 무장된 데몬 쪽 감시를 건드리지 못해 생겼다. 프로세스 경계를 넘는 설정에는 **끄는 말**이 있어야 한다.
5. **PowerShell 5.1 은 BOM 없는 파일을 ANSI 로 읽는다.** 한글이 든 스크립트를 scratchpad 에 쓰면
   `Missing closing '}'` 같은 엉뚱한 파서 오류가 난다(`dev/app/tool/capture-window.ps1` 머리말의 경고 그대로).
   실기용 임시 스크립트는 **ASCII 로만** 쓴다.
6. **`Get-Process` 의 pid 는 좀비를 본다.** 핸들을 쥔 프로세스가 있으면 이미 끝난 pid 도 살아 있어 보인다.
   "남은 프로세스 0" 은 `Get-CimInstance Win32_Process`(끝난 프로세스를 안 돌려준다)로 세야 한다.
7. **`taskkill /F` 로 앱을 죽여도 `pixel-office.db-wal`/`-shm` 이 남는다.** 다음 정상 종료에서 사라진다(무해).

## 남은 것

- **`process.exit(0)` 이 가끔 안 끝난다.** 콘솔에서 띄운 데몬 한 번에서 `[daemon] bye` 를 찍고도 프로세스가
  남았다(포트는 해제, 자식 0, CPU 0 — node-pty/ConPTY 의 네이티브 종료가 매달린 것으로 보인다. 같은 실행에서
  `conpty_console_list_agent` 의 `AttachConsole failed` 가 같이 났다). **앱 경로에서는 한 번도 안 봤고**,
  본다 해도 앱이 8초를 기다린 뒤 `taskkill /T /F` 로 치운다. 콘솔 실행에서 재현되면 따로 볼 것.
- **"계속 일하기" 를 앱 실행 중에 *끄면*** 데몬의 부모 감시가 **켜지지는 않는다**(그 데몬은 애초에
  `PIXEL_PARENT_PID` 없이 떴다). 정상 종료는 앱이 직접 끄므로 문제가 없고, 그 상태에서 앱을 **강제 종료**하면
  다음 기동까지 고아가 남는다. 대칭으로 "다시 지켜봐라" 를 보내려면 `hello{parentPid}` 재전송 또는
  `daemon.watchParent` RPC 가 필요하다 — 실사용 빈도가 낮아 미뤘다.
- **Codex 멤버로는 안 돌려 봤다.** 이번 조직은 셋 다 Claude 였다(확인용 세션만 Codex). Codex 의 `resume`·
  `[RESUMED]` 제출 확인은 T42 가 실기로 덮어 두었지만, **수명 주기**(suspended → 말없이 복구)는 Codex 로 미확인.
- **확인용 세션 경고 한 줄**: `[office] 사용량 확인용 세션(claude): /usage 화면이 뜨지 않았습니다 — CLI 문구가
  바뀌었을 수 있습니다` 가 마지막 실행에 한 번 나왔다(T43 영역, 사용량 숫자는 계속 들어왔다). 관찰 대상.
