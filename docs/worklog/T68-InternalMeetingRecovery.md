# T68 — 내부 참석자 연결과 회의 자동 복구

## 문제

회의는 삭제된 옛 팀장 3명의 ID를 보관하고, 현재 팀장들은 다른 ID로 출근해 있었다. 재개는 옛 ID만 확인하고, 부장 AI에는 실제 부서 조회·복구 도구가 없었다. 첫 지시 전이라 대화 ID가 없는 Codex도 앱 재실행 때 복구 실패로 처리했다.

## 변경

- 회의를 시작할 때 참석자의 이름·직급·상사를 함께 기록한다. 복구는 현재 부서 목록과 대조해 분명한 대체자를 연결한다. 기존 이름만 저장된 회의도 현재 직속 팀장에 연결할 수 있다.
- 원래 지시, 회의 ID, 업무 ID, 이미 제출된 의견을 유지하고 교체 이력을 남긴다. 의견을 제출한 자리는 같은 의견을 다시 요구하지 않는다.
- 후보가 여러 명이면 자동으로 아무나 선택하지 않는다. 부장 AI가 현재 목록을 조회하고 연결할 수 있다. 다른 부서·역할, 중복 자리, 활동 중인 참석자 강제 교체, 오래된 회의 요청은 거절한다.
- 부장 전용 `office_status`는 현재 부서의 실제 멤버와 작업 상태를 반환한다. 인증 토큰과 실행 설정은 제외한다.
- 부장 전용 `meeting_resume`과 사용자 화면의 `workflow.resume`은 같은 복구 경로를 쓴다. 종료된 참석자는 다시 시작하며, 동시에 들어온 복구는 한 번만 처리한다.
- 필요한 참석자가 준비되면 중단된 회의를 자동으로 이어간다. 자동 연결이 안 되면 부장에게 내부 복구 요청과 도구 사용법을 전달한다.
- 첫 지시 전 Codex는 새 세션으로 다시 시작한다. 중단 상태의 부장에게 기존 작업 재실행 지시를 보내 팀을 다시 해산·생성하게 하지 않는다.
- 화면에서 삭제된 참석자를 단순 ‘의견 제출 대기’로 표시하지 않는다. 복구된 문제의 경고와 열려 있던 오류 팝업은 자동 해제한다. 별개의 오류나 사용자 대화 창은 닫지 않는다.
- 실행 단계에서도 배정 업무 진행·선행 업무 대기·담당 업무 완료·부장의 보고 대기를 구분해 표시한다.

## 검사

- 참석자 교체 후 의견 보존, 옛 저장 형식의 3명 연결, 잘못되거나 중복된 연결 거절, 동시 복구, 부서 조회의 정보 범위, 실제 MCP 요청, 첫 대화 전 Codex 복구, 준비 완료 후 자동 재개를 검사했다.
- 해결된 오류 팝업의 자동 해제와 대기열 제거, 다른 오류 창 보존을 검사했다.
- 서버 타입 검사 통과. 전체 1,251건 통과·15건 건너뜀.
- 앱 코드 검사 문제 없음. 전체 820건 통과·1건 건너뜀. Windows 실행 파일 생성 성공.

## 실제 앱 확인

- 반영 전 현재 기록을 로컬 DB 백업으로 보관했다. 실행 중인 응답이나 승인 대기가 없는 중단 상태에서 서버 수정본을 적용했다.
- 기존 회의 `w_83cabc98-a359-4a04-b154-9697aa96987b`와 원래 작업 `task#1`을 유지했다. 옛 참석자 3명이 현재 팀장 3명에 자동 연결됐으며 새 회의는 만들지 않았다.
- 세 Codex 팀장 모두 실제 대화 ID가 생성됐다. 회의 의견 0건 → 1차 3건 → 2차까지 총 6건을 확인했다.
- 부장이 회의 계획을 확정하고 `executing` 단계로 전환했다. 문서QA 업무 배정과 백엔드·프론트의 선행 업무 대기를 확인했다.
- 실행 중인 실제 MCP에 접속해 부장 조회 도구의 응답과 복구 도구의 제공 여부를 확인했다.
- 마지막 팝업 표시 수정은 작업 관리 프로그램을 유지한 채 화면 프로그램만 교체했다. 서버 PID 11124와 AI 세션이 유지됐고 새 화면으로 부모 감시가 다시 연결된 것을 확인했다.
- 사용자 업무 전체가 완료됐다는 의미는 아니다. 회의 복구와 실제 업무 배정까지 확인했으며, 진행 중인 업무를 종료하지 않았다.
