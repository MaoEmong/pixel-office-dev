## D-16 · 2026-09-15 · 세션 hooks `timeout`은 86400초, 만료 시 TUI 프롬프트가 폴백

## D-24 · 2026-09-16 · Codex 부팅 완료는 화면(prompt-ready)으로 판정, SessionStart는 첫 프롬프트 때 온다
- 맥락(T20): Codex hooks의 `SessionStart`는 부팅 시가 아니라 **첫 프롬프트 제출 시** 발화. hook만 기다리면 멤버가 영원히 `starting`이라 첫 지시가 안 들어감.
- 결정: Codex 멤버는 `Office.watchBootReady()`가 ScreenModel prompt-ready(다이얼로그 없음, `model: loading` 아님)를 보고 `starting → idle`로 올린다. SessionStart가 먼저 오면 그걸로.
- 참고: node-pty는 PATH의 `codex` 셸 shim(.cmd/.ps1)을 못 띄움 → `config.codexExe`는 실제 `codex.exe` 경로여야 함(T22에서 npm 전역 경로 자동 탐색).

## D-25 · 2026-09-16 · 턴 종료 hook 이 없으면 화면으로 idle 을 판정한다(`idle{summary:'screen-idle'}`)
- 맥락(T23 함정 1): Codex 사용량 한도 안내는 화면에만 찍히고 `Stop` hook 이 오지 않는다. 데몬은 `UserPromptSubmit` 으로 올려 둔 `working` 을 내려 줄 근거가 없어 멤버가 퇴근할 때까지 `working` 에 갇힌다 — ① 사무실 표시가 틀리고 ② `InputQueue.isIdle` 게이트가 안 열려 다음 지시가 큐에 머문다. 원인은 한도가 아니라 "턴 종료 hook 없이 프롬프트로 돌아오는 화면" 일반이고, Claude 도 턴이 이상하게 끊기면 같은 일이 난다.
- 결정: `Office.watchScreenIdle()` — 엔진 공통, 멤버당 타이머 하나, 500ms 폴링(`watchBootReady`/`watchInterrupted` 와 같은 모양). status 가 `working`/`waiting_approval`/`waiting_answer` 이고, **열린 pending 이 하나도 없고**, 화면에 다이얼로그·busy 표시가 없고 prompt ready 이고, 그 사이 새 hook 이 도착하지 않은 상태가 **3초 연속**이면 `idle{summary:'screen-idle'}` + status `idle`. 조건이 하나라도 깨지면 창을 닫고 처음부터 다시 잰다. 세션이 끝나면 타이머를 멈춘다.
- 버린 대안: ① 엔진별(Codex 전용) 폴백 — 원인이 엔진이 아니라 화면이다. ② status 만 바꾸고 이벤트는 안 남기기 — 앱 로그에서 "왜 내려왔나"를 설명할 수 없다. ③ 창을 더 짧게(1초) — 화면이 잠깐 준비로 보이는 구간(도구 출력 사이)에서 오발화 위험.
- 근거: worklog/T23b-defects.md, `test/office/ScreenWatch.test.ts`(실측 픽스처 `codex/usage-limit.txt` · Claude 준비 화면). 보류·busy·다이얼로그 중에는 발화하지 않는 것을 테스트로 고정.

## D-26 · 2026-09-16 · `approval-prompt` 은 "통과" 가 아니라 "막힘" 이다 — `dialogPassed` 대신 `blocked`+`dialogBlocked`
- 맥락(T23 함정 2, T21 후속): Claude 2.1.270 은 `PermissionRequest` hook 을 보류하는 동안에도 자기 TUI 허가 프롬프트를 띄운다. ScreenModel 은 이걸 `approval-prompt` 로 감지하고 D-23 대로 `suggestedKeys: []` 를 준다(키 안 나감 = 안전). 그런데 InputQueue 가 빈 키 시퀀스를 "보냈다" 치고 `dialogPassed` 를 emit 해 `daemon.notice` 에 `passed first-run dialog (approval-prompt)` 가 허가 대기 내내 2초마다 찍혔다(실기 7회).
- 결정: InputQueue 는 `suggestedKeys` 가 비어 있으면 키를 보내지 않고 `dialogPassed` 도 내지 않는다. 대신 ① `blocked('dialog')`(다른 blocked 이유와 같은 5초 계량, 큐에 기다리는 항목이 있을 때만) ② 새 이벤트 `dialogBlocked(kind)` — **그 다이얼로그가 사라질 때까지 kind 당 한 번**.
