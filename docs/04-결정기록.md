## D-01 · 2026-09-14 · 연동 방식: 실제 CLI TUI를 pty로 띄운다
- 맥락: rev 1 설계는 Agent SDK / codex app-server 프로그램 연동.
- 결정: `claude` / `codex` 인터랙티브 CLI를 node-pty에 그대로 띄우고 타이핑으로 지시한다. 상태는 hooks로.
- 버린 대안: Agent SDK(별도 크레딧·터미널 없음), app-server, hooks만(지시 불가).
- 근거: 사용자 의도("그냥 cli를 켜서 거기다 명령"), 구독 그대로 사용, 터미널 화면 공짜. 실측 02 전 항목 통과.

## D-12 · 2026-09-14 · node-pty ConPTY 자연 종료 시 내부 리소스를 직접 해제
- 맥락: T01 통합 테스트에서 `/exit`로 자식이 끝나도 node-pty 1.1.0(win32)이 conout 워커 스레드·pseudoconsole 핸들을 풀지 않아 데몬 프로세스가 종료되지 않음. `proc.kill()`로 우회하면 `conpty_console_list_agent`가 포크되어 stderr 스택과 5초 대기.
- 결정: `onExit`에서 `releaseConptyResources(proc)`로 내부 필드 3개를 직접 해제, 필드 형태가 바뀌면 `proc.kill()` 폴백. node-pty 업그레이드 시 재확인 항목.
- 근거: worklog/T01-PtyManager.md.

  | 같은 멤버·같은 종류가 1초 안에 연달아 | 6건 / 88건 (6.8%) |
- 결정: **코얼레스(합치기)를 넣지 않는다.** 근거 셋.
  1. **양이 문제가 아니다.** 부서 전체 31.3건/분이면 앱 링버퍼 2,000건을 채우는 데 **64분**이고, 피크도 1초에 6건이다. 위젯 재빌드·로그 탭 스크롤·WS 트래픽 어디에도 부담이 없다(실기 내내 앱이 매끄러웠다). 멤버 한 명이 보내는 양은 **1초에 최대 2건**이다.
  2. **합칠 만한 후보 6건이 전부 합치면 안 되는 것들이었다.** 3건은 `running{tool:'mcp__team__create_team'}`·`hire` 가 0.6~0.8초 간격으로 **두 번 불린 것**(진짜 도구 호출 두 번 — 하나로 줄이면 "팀원 둘을 고용했다" 가 하나로 보인다). 나머지 3건은 `running{cmd}` **0ms** 뒤의 `running{waiting:'shell-lock'}` 인데, 이건 "시작했다 → 막혔다" 라는 **서로 다른 사실**이고 앱 말풍선 `⏳ 셸 대기 중 (락: …)` 이 바로 이 두 번째 이벤트다(T29 결함 ③ → T37 수정 → T39·T31 실기 확인). 합치면 방금 고친 화면이 도로 망가진다.
  3. **합치면 잃는 것이 크다.** `seq` 는 재접속 replay(`hello{since}`)·`events.query` 백필(D-21)·중복 제거의 기준이라, 합치는 순간 "어디까지 봤나" 가 이벤트 개수와 어긋난다. 게다가 이벤트는 사무실 애니메이션의 입력이기도 하다(말풍선·모니터·이동) — 시간 축을 뭉개면 움직임이 건너뛴다.
- 버린 대안: ① 데몬에서 같은 멤버·같은 kind 를 N ms 창으로 합치기 — 위 2·3. ② 앱에서만 렌더 스로틀(16ms 배치 repaint) — 지금 부담이 없어 넣을 이유가 없고, 넣는 순간 위젯 테스트 30여 개의 기대가 바뀐다. ③ `term` 처럼 replay 대상에서 빼기 — 이벤트는 사무실의 유일한 이력이라 불가.
- 되돌릴 조건(다음에 다시 볼 기준선): **부서 하나가 5분 평균 300건/분을 넘거나**, 임의의 1초 창이 **50건**을 넘거나, 앱 프레임이 눈에 띄게 끊기면. 그때는 "합치기" 보다 **앱 쪽 렌더 배치**(데몬 이벤트·seq 는 그대로 두고 repaint 만 모으기)를 먼저 본다.
