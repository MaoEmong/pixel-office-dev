# 환경·CLI 인증 문제 해결 (T57)

## 시작할 수 없을 때

앱은 새 데몬 시작 전에 package.json, Node.js 24 이상, SQLite,
tsx·node-pty·ws·qrcode·zod·xterm·MCP SDK 로딩을 확인한다.
확인된 설치 문제는 실패 화면에 복구 방법을 바로 표시한다. 환경을 고친 뒤 '다시 시도'를 누른다.
이미 실행 중인 데몬에 붙는 경우에는 새 시작 검사를 하지 않는다.

| 문제 | 처리·복구 |
|---|---|
| Node 실행 불가 | Node.js 24 이상 설치, 앱 재실행. 필요하면 PIXEL_NODE에 실행 파일 전체 경로 지정 |
| Node 24 미만 | 지원 버전으로 교체 후 재실행 |
| package.json 누락·손상 | 저장소 전체를 받고 dev/daemon 폴더 확인 |
| 의존성 누락 | dev/daemon에서 npm ci 후 다시 시도 |
| node-pty 로딩 실패 | Node·OS에 맞는 네이티브 모듈 설치 확인. npm 설치 로그에서 권한·빌드 실패 확인 |
| 검사 시간 초과 | Node 실행·보안 프로그램 차단 확인 후 재시도 |
| 포트 충돌·데이터 폴더 권한·DB 오류 | daemon.log의 실제 오류 확인. 다른 프로세스를 자동 종료하거나 DB를 자동 삭제하지 않음 |

새 설치로 열린 앱의 PATH에 경로가 없으면 앱을 다시 연다.
Windows 소스 빌드는 Flutter, Visual Studio C++ 데스크톱 개발 도구, 심볼릭 링크 권한이 별도로 필요하다.
이는 앱이 실행되기 전의 빌드 조건으로 런타임 검사 대상이 아니다.

## CLI 설치·로그인

앱 상단 ⋮ → '환경 점검 · CLI 로그인'에서 확인한다.
사용할 엔진만 설치하면 된다. Codex 미설치는 Claude 사용을 막지 않는다.
설치·로그인 변경 후 '다시 검사'를 누른다.

| 상태 | 행동 |
|---|---|
| 미설치 | 공식 CLI 설치, PATH 또는 PIXEL_CLAUDE_EXE/PIXEL_CODEX_EXE 확인, 앱 재실행 |
| 로그아웃 | 새 터미널에서 claude auth login 또는 codex login 실행 |
| 확인 불가 | 네트워크·권한·CLI 버전 확인. 로그아웃이라고 단정하지 않음 |
| 정상 | 상태 명령에서 인증 확인. 실제 모델 사용 가능·남은 한도를 보장하는 검사는 아님 |

사용자 RPC의 부서/팀/멤버 생성, 멤버 지시·재고용·재시작, workflow 대화·시작·재개는
관련 엔진의 미설치·로그아웃이 확인되면 실행 전에 거부한다. 상태 확인 불가만으로는 막지 않는다.
내부 MCP create_team/hire도 설치·인증 검사 후 실행한다. 자동 세션 복구는 허용 엔진 정책을 검사하며,
진행 중 인증 만료·한도 상태를 전부 대신 검사하는 것은 아니다.
진행 중 인증 만료·요금 한도·서버 오류는 CLI 터미널과 로그도 확인한다.
오류 뒤 요청을 반복하기 전 실제 실행 결과를 확인한다.

## 특정 프로젝트 멤버만 로그인 대기 중일 때

프로젝트 세션은 .pixel-office/sessions/<멤버 ID>/claude 또는 codex를 별도 홈으로 쓴다.
캐릭터를 선택한 뒤 환경 점검에서 '선택 멤버 검사'를 누른다.
기존 세션 홈에서 상태를 검사하고 로그아웃이면 정확한 홈을 지정한 로그인 명령을 보여준다.
새 터미널에서 안내된 명령을 실행한 뒤 다시 검사한다. 환경변수는 그 터미널에만 적용한다.
필요하면 해당 멤버를 재고용·재시작한다. 세션 폴더나 인증 파일은 삭제하지 않는다.

점검은 CLI 상태 명령만 사용한다. 비밀번호·토큰·이메일을 결과에 표시하지 않고,
라이브러리 자동 설치나 인증 정보 덮어쓰기를 수행하지 않는다.

## 사용할 엔진 선택

환경 점검의 사용 엔진 설정은 기본으로 부장과 같은 엔진만 허용한다.
Claude만 사용하거나 Codex만 사용한다면 해당 항목을 선택한다.
두 엔진을 함께 사용하는 경우에만 둘 다 사용을 선택한다. 인증 성공은 결제 여부를 뜻하지 않는다.
사용 설정에서 차단됐다는 오류가 나면 설정을 확인한다. 허용하지 않은 엔진은 새 멤버 생성·재시작·복구·새 지시에 사용할 수 없다.
실행 중 작업은 강제 종료하지 않는다. 다른 엔진을 쓰던 기존 세션은 기록을 보존하며 복구 불가 상태로 안내할 수 있다.

## 저장·원격 연결 실패

설정 저장 실패 배너가 나타나면 데이터 폴더 쓰기 권한과 남은 공간을 확인하고 '다시 저장'을 누른다.
실패한 설정은 재시도할 때까지 메모리에 유지한다. 계속 일하기 스위치는 실패하면 이전 값으로 돌아간다.
잠금 파일 저장 실패 화면에서는 원인을 해결한 뒤 '다시 시도'를 누른다. 잠금 없이 앱을 실행하지 않는다.

원격 연결만 시작하지 못하면 로컬 사무실은 사용할 수 있다.
'기기 연결 · 원격 조작'에서 오류를 확인하고 포트 충돌·remote-devices.db 쓰기 권한 문제를 해결한 뒤
'원격 연결 다시 시작'을 누른다. 등록된 기기 DB를 삭제할 필요는 없다.

멤버 출근 중 지시문 저장·CLI 생성이 실패하면 해당 멤버는 오류 상태로 남으며 재고용할 수 있다.
새 부서·팀 생성 자체가 실패했다면 그 생성 중인 부서·팀은 취소된다. 기존 작업 기록은 삭제하지 않는다.

## 프로젝트 이동·CLI 준비 실패·자원 제한

프로젝트 경로가 사라지거나 디렉터리가 아니면 새 지시·재시작·복구를 거부한다.
모든 멤버를 퇴근시킨 뒤 '프로젝트 폴더 다시 연결'에서 이동한 원래 프로젝트를 지정한다.
폴더 연결은 파일을 이동·삭제하지 않는다. .pixel-office를 함께 이동해야 프로젝트 전용 세션을 찾을 수 있다.

CLI가 3분 동안 준비 화면에 도달하지 못하면 해당 멤버를 오류로 표시하고 대기 작업·질문·세션을 정리한다.
환경 점검과 터미널에서 설치·로그인·CLI 화면을 확인하고 해결 후 재고용한다.
서비스의 사용량 제한·계정 인증 문제를 시간 초과만으로 단정하지 않는다.

기본 제한은 멤버 CLI 16개, 부서별 팀 8개다. 환경 점검에서 각각 1~64개, 1~32개로 저장할 수 있다.
제한을 넘으면 생성 전에 안내하며, 실행 중 세션은 자동 종료하지 않는다.
복구 시에도 제한을 적용하므로 초과 멤버는 다른 멤버를 퇴근시키거나 제한을 조정한 뒤 재고용한다.

작업 시작·대화 전송이 실패하면 상태·작업 저장을 함께 되돌린다.
앱에서 응답 시간 초과·연결 오류 후 같은 작업 시작·대화를 재시도하면 요청 ID를 재사용해 중복 생성하지 않는다.
성공한 뒤 다시 보내는 것은 새로운 사용자 요청으로 처리한다. 직접 RPC를 사용할 때는 requestId를 함께 보낸다.

오류 패널은 해결 안내를 먼저 표시하고 원시 오류·로그는 '오류 상세'에서 펼친다.
지시 바의 오류 표시를 누르면 전체 오류 패널을 열 수 있다. 데몬 오류 알림은 닫기 전까지 유지된다.

## 회의·업무 배정·제출 복구

회의 소집과 의견 차례 전환은 저장 성공 후 참석자에게 전달한다. 실패한 요청은 저장을 되돌려 다시 시도할 수 있다.
업무 생성과 계획의 taskId 연결, 완료 보고와 계획 상태도 함께 저장한다.
업무 배정이 실패하면 문제를 표시한다. 원인을 해결한 뒤 '대화 · 회의 · 작업'의 **업무 배정 재시도**로 기존 계획에서 미배정 업무만 이어 간다.
이미 실행한 업무가 blocked/aborted로 보고된 경우에는 작업 취소 후 보완 논의를 시작한다.

CLI가 지시를 받았는지 확인하지 못하면 멤버 패널에 **제출 확인 필요** 카드가 표시된다.
'지시 재제출'은 입력 상자에 남은 지시에 Enter만 보내며 같은 작업을 다시 붙여넣지 않는다.
입력 상자를 수정했거나 CLI가 확인 창을 기다리면 터미널에서 먼저 확인한다.
다음 지시는 제출 확인/복구가 끝날 때까지 기다린다. 세션 재시작 후에는 이전 입력 상자를 보장할 수 없어 터미널 확인이나 중단이 필요할 수 있다.

실행 중 프로젝트를 이동하면 로그 저장도 원래 루트를 재생성하지 않는다. 원래 프로젝트를 다시 연결하거나 폴더를 복구한다.

## 응답 유실 후 재시도

앱은 생성·지시·승인 등 주요 변경 요청의 식별자를 PC의 rpc-retries.json에 저장한다.
모바일 브라우저는 명령 내용 대신 요청 내용의 해시와 요청 식별자만 IndexedDB에 저장한다.
응답 유실 뒤 같은 요청을 보내거나 화면을 다시 열어 재시도해도 동일 식별자를 사용한다.
성공 응답 이후의 새 요청은 새 식별자를 받는다. 갱신 화면만 실패한 경우에는 요청이 성공했다는 안내를 표시한다.

데몬 재시작/저장 실패로 실행 결과를 확정할 수 없는 요청은 자동으로 반복하지 않는다.
'실행 결과를 확인하세요' 안내가 나오면 작업·회의·승인 상태를 먼저 확인한다. 요청 기록 파일을 무작정 지우고 다시 보내면 중복 실행될 수 있다.
직접 RPC를 쓰는 클라이언트는 requestId를 직접 유지해야 보호를 받는다.

## 저장 상태와 백업

상단 ⋮ → **환경 점검 · CLI 로그인 → 저장 상태 · DB 백업**에서 현재 저장 오류를 확인한다.
디스크 공간·권한·프로젝트 경로를 복구한 뒤 다시 검사한다. 파일 기록이 다시 성공하면 오류 상태가 해제된다.
데몬 로그는 실패 후 30초 간격으로 다음 기록에서 재시도한다.
프로젝트 events.jsonl·hook 로그·daemon.log는 파일당 약 5MiB와 이전 파일 3개까지 보관한다.
종료된 과거 workflow는 90일 보존하며 부서의 최신 workflow와 진행 중 workflow는 유지한다.

SQLite는 기동 시 무결성을 검사한다. DB의 일별 백업 및 '지금 DB 백업' 결과는 데이터 폴더의 backups에 최대 3개 저장한다.
백업 파일 이름의 날짜·시간은 UTC다. SQLite 백업에는 WAL에 저장된 변경도 포함된다.
DB 백업에는 프로젝트 파일·CLI 세션 홈·원격 기기 등록 DB가 포함되지 않는다. 전체 이사를 위해서는 이 자료를 함께 보관해야 한다.

DB를 복구하려면 다음 순서를 따른다.

1. 앱과 데몬을 종료한다. '앱을 닫아도 계속 일하기'가 켜져 있다면 데몬도 별도로 종료한다.
2. 현재 데이터 폴더 전체를 다른 곳에 복사해 원본을 보존한다.
3. pixel-office.db 및 같은 이름의 -wal/-shm 파일을 별도 보관 폴더로 옮긴다. 실행 중에는 옮기지 않는다.
4. 선택한 backups/office-*.db를 데이터 폴더의 pixel-office.db로 복사한다.
5. 앱을 켜고 작업·세션 상태를 확인한다. 백업 이후 실행 결과는 프로젝트 파일과 CLI 기록에서도 확인한다.

예상하지 못한 비동기 처리 오류는 안내를 표시하고 데몬을 정리한다. 다시 연결 후 실행 결과를 확인한다.
실제 서비스 장애·인증 만료·전원 차단의 모든 경우를 자동으로 복구한다는 보장은 아니다.

로컬 중복 방지 기록은 90일, 원격 기록은 7일 범위로 유지한다. 그보다 오래된 미확정 요청은 자동 재전송하지 않는다. 진행 중인 계획이 참조하는 보고는 보존 정리에서 제외한다.
