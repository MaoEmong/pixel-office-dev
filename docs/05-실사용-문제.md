## U-01 · 2026-10-08 · 말풍선이 한 박자 늦는다 — 승인해도 다음 이벤트가 올 때까지 "승인 대기" 가 남는다

### 증상

승인 대기 말풍선을 보고 **승인을 눌렀는데도 말풍선이 그대로 "승인 대기"** 다. 그 멤버에게 **다음
말풍선이 올 때** 비로소 바뀐다. 사용자 관찰: 승인뿐 아니라 **말풍선으로 표시되는 것 대부분**이 그렇다.

즉 말풍선이 "지금 상태" 가 아니라 "마지막으로 일어난 일" 을 보여 주고 있고, 둘이 어긋나는 구간이 생긴다.
사용자 입장에서는 **내가 누른 게 먹었는지 알 수 없다** — 가장 불안한 종류의 지연이다.

### 재현

1. 부서를 만들고 부장에게 쓰기가 필요한 일을 시킨다.
2. 허가 카드가 뜨고 캐릭터 말풍선이 "승인 대기" 가 된다.
3. 인박스(또는 내 책상)에서 승인한다.
4. **말풍선은 그대로다.** 멤버가 다음 행동(도구 호출·텍스트·idle)을 해서 이벤트가 하나 더 올 때까지 안 바뀐다.

### 짚이는 자리 (코드만 읽은 추정)

말풍선 텍스트의 출처가 **이벤트**다:

- `dev/app/lib/state/office_state.dart` — `latestEvent: Map<String, OfficeEvent>` 주석이 그대로
  "멤버별 마지막 이벤트(**말풍선**)" 다. 이벤트가 올 때만 갱신된다.
- `dev/app/lib/office/office_scene.dart` — `summary` → `bubbleText`(28자 컷), `isAlert` 는
  `waiting_approval / asking / reporting` 일 때.

그런데 **승인 응답은 상태(status)를 바꾸지 이벤트를 새로 만들지 않는 것으로 보인다.** 콘솔에서도 두 흐름이
따로 찍힌다 — `status 부장 → working (working)` 과 `#14 running …` 은 다른 줄이다. 그래서
**status 는 즉시 바뀌는데 말풍선은 안 바뀐다.**

같은 성질이면 질문 답변(`answer`)·거부(`deny`)·중단(`int`)도 똑같이 늦을 것이다 — 사용자가 "대부분
그렇다" 고 한 것과 맞는다. **확인 안 함**(실사용 중이라 건드리지 않았다).

### 후보 수정

세 갈래가 있고 성질이 다르다.

1. **앱에서 status 를 같이 본다** — 말풍선을 `latestEvent` 단독이 아니라 `(status, latestEvent)` 합성으로
   만든다. 서버를 안 건드려 제일 싸고, "상태가 바뀌면 말풍선도 바뀐다" 가 구조적으로 보장된다.
   대신 "무슨 일이 있었나" 와 "지금 어떤가" 를 한 칸에 섞는 규칙을 새로 정해야 한다.
2. **데몬이 해소 이벤트를 쏜다** — 승인·거부·답변 때 그 멤버의 이벤트를 하나 발행한다. 사무실 로그에도
   "승인됨" 이 남아 이력이 좋아진다. 대신 이벤트 수가 늘고(D-41 에서 코얼레스를 안 넣기로 한 전제와
   같이 봐야 한다) PROTOCOL 이 바뀐다.
3. **앱에서 status 변화 때 말풍선을 무효화** — 가장 작지만 "빈 말풍선" 구간이 생겨 어색할 수 있다.

**지금 기운 쪽은 1 번**이다 — 증상이 "대부분의 말풍선" 이라면 개별 이벤트를 추가하는 것(2)보다 **파생
규칙 한 곳**을 고치는 게 맞다. 다만 레이아웃 v2(D-42~44)가 말풍선·모니터·범례의 역할을 나눠 놨으므로
`docs/design/레이아웃-v2.md` 와 01 §3 "캐릭터 상태 3중 표현" 을 먼저 읽고 정할 것.

### 상태

**고침 — 2026-10-11, T52** (커밋 `435827f`). 후보 1번(앱이 status 를 같이 본다)으로 갔고, 데몬 쪽에도 같은 병이 하나 더 있어 같이 고쳤다.

- **확인된 원인**: 추정이 맞았다. 데몬의 `settlePending`(`BaseHooksAdapter.ts`)이 `setStatus('working')` 만 하고 이벤트를 내지 않는다 — 승인·거부·답변 전부 같은 자리다.
- **앱**: `waiting_approval`·`asking` 이벤트를 "지금 기다린다는 상태 주장" 으로 본다. status(raw·파생)가 대기가 아니고 **열린 pending 도 없으면** 낡은 것이라 지금 상태로 바꿔 말한다(`office_scene.dart` `isStaleWaitEvent` → `summarize`·`isAlertFor`). 승인하면 말풍선이 곧바로 `…`(작업 중)이 된다.
  열린 pending 을 같이 보는 이유는 T19b — `ask_user` 는 턴을 붙잡지 않아 status 가 먼저 `working` 으로 돌아온다. status 만 보면 살아 있는 질문 말풍선을 지운다.
- **데몬**(문서에 없던 것): "셸 대기 중(◷)" 말풍선도 같았다. 줄을 섰던 명령이 락을 넘겨받아도 이벤트가 없어 **실행 중에도 대기 말풍선**이었고, 명령이 끝나도 다음 도구까지 그대로였다. 넘겨받을 때 `running{cmd}` 을 한 번 더 낸다(`Office.noticeShellGranted`). 즉시 획득과는 시간이 아니라 **줄을 섰는지**로 가른다(`ShellMutex` `granted` 의 `queued`).
- **건드리지 않은 것**: `▶ 명령` 이 명령이 끝난 뒤에도 다음 이벤트까지 남는 것. 그건 "마지막으로 한 일" 이라 틀린 말이 아니다 — 문제였던 것은 **끝난 대기**를 계속 말하는 것이다.
- **확인**: 단위(장면·요약 규칙) + 데몬 `ShellMutex.test.ts`. **실제 화면에서는 아직 못 봤다** — 새 빌드로 승인 한 번 눌러 보면 된다.

## U-02 · 2026-10-08 · 서브 AI 의 허가를 전부 사람이 받는다 — 안전한 것은 자동, 위험한 것만 묻기

### 증상

**이 프로젝트를 시작한 이유 자체와 부딪히는 문제다**(번거로움을 줄이려고 만들었는데 번거롭다).

사용자 말 그대로: *"부장 AI 와 대화하면서 승인을 내리는 건 괜찮은데, 서브 AI 들의 권한 허가 여부도
계속 내가 하는 게 너무 번거롭다."* 부장 하나를 상대할 때는 견딜 만한데, 팀장·팀원이 붙으면 허가 카드가
**사람 수만큼 곱해진다.** 대부분은 `ls`·`cat`·`mkdir` 같은 시시한 것들이다.

바라는 것: **기본적인 권한은 모두 주고, 위험한 것만 사람에게 묻는다.**

### 지금 왜 이런가 (설계된 동작이다, 버그 아님)

D-32 3번: *"**셸 허가(Bash 승인)는 계속 사용자에게.** 보고 체계와 무관한 안전 문제. 카드가 늘어나므로
'이번 세션 항상 허가' 를 팀 단위로 넓히는 옵션을 검토(T34)."*

즉 **직급과 무관하게 전부 사용자** 가 현재 정책이고, 카드가 늘어나는 문제도 이미 예견돼 있었다
(그 "검토" 가 아직 안 된 상태다). 그래서 이 항목은 버그 수정이 아니라 **D-32 의 일부를 뒤집는 결정**이
필요하다 → 새 D-## 가 있어야 한다.

### 짚이는 자리 — 부품은 이미 다 있다

1. **위험 판별기**: `dev/daemon/src/adapters/mapping.ts` 의 `DANGER_PATTERNS` (17개) +
   `isDangerousCommand()` · `dangerousReasons()`. 유닉스와 PowerShell 을 같은 표에 담았다 —
   `rm -r/-f` · `sudo` · `chmod -R` · `chown -R` · `git push --force` · `git reset --hard` ·
   `git clean -fd` · `truncate` · `dd` · `mkfs` · `Remove-Item -Recurse/-Force` · `del /s` · `rd /s` ·
   `format` · 쓰기 리다이렉트(`>`·`>>`) · 피연산자 둘 이상인 `mv`.
2. **읽기 전용 판별기**: `codexMapping.ts` 의 `isReadOnlyCommand()`. 이미 위험 판별을 안전망으로 쓴다.
3. **결정을 돌려주는 길**: `src/hooks/decisions.ts` 의 `allow()` / `deny()` — hook 이 결정을 반환할 수
   있다(D-04). **자동 허가의 레버가 이미 있다.**

지금 위험 판별기는 **경고 표시용으로만** 쓰인다. 파일 머리에 그렇게 적혀 있다:
*"이 판별은 **경고용**이다(앱의 허가 카드 `위험` 태그) … 여기서 무엇을 막지는 않는다."*

즉 **붙이는 일만 남았다** — 판별 결과를 pending 생성 지점에서 보고 `allow()` 로 흘리면 된다.

### ⚠ 가장 중요한 함정 — 판별기의 "틀리는 방향" 이 뒤집힌다

지금 위험 판별기는 **과탐지(false positive)가 싼** 전제로 만들어졌다. 같은 주석에 이렇게 적혀 있다:

> 애매하면 "위험" 쪽으로 기운다 — **사람이 한 번 더 보는 것이 싸다.**

경고 표시용일 때는 맞는 설계다. 그런데 **자동 허가의 기준으로 쓰는 순간 비용이 반대가 된다** —
이제 비싼 쪽은 **미탐지(false negative)** 다. "위험한데 위험으로 안 잡힌 명령" 이 **사람에게 안 물어보고
그냥 실행된다.**

구체적으로 알려진 구멍:
- **셸 래퍼 안을 안 본다.** `isReadOnlyCommand` 주석: *"셸 래퍼(`bash -lc \"...\"`)는 안을 파싱하지 않고
  false."* 위험 판별은 문자열 정규식이라 `bash -lc 'rm -rf ~'` 같은 것이 표에 걸릴지 **확인해야 한다.**
- **문자열 기반**이라 변수·치환·인코딩으로 우회할 수 있다(`$HOME`, `eval`, base64 …).
- 표에 없는 파괴적 명령(예: `find … -delete`, `xargs rm`, `> /dev/sda`, 패키지 매니저 전역 설치 등).

그래서 **판별기를 그대로 자동 허가에 쓰면 안 된다.** 자동 허가 기준은 **화이트리스트(허용 목록)** 여야
한다 — "위험하지 않으면 통과" 가 아니라 **"안전하다고 아는 것만 통과"**. `isReadOnlyCommand` 가 이미
그 모양이다(모르는 명령은 false).

### 후보 설계

축을 여러 개 섞을 수 있다. 하나만 고를 필요는 없다.

1. **안전 목록 기반 자동 허가** — `isReadOnlyCommand` 처럼 **아는 것만** 통과. 모르면 묻는다.
   가장 안전하고, 사용자가 말한 "시시한 것들" 의 대부분을 덮는다.
2. **작업 폴더 경계** — 부서 cwd **안** 의 쓰기는 자동, **밖** 은 묻는다. 강력하고 설명하기 쉽다.
   그리고 **codex 는 이미 그렇게 동작한다** — T48-3 M5 실측: 작업 폴더 안 쓰기는 카드가 안 떴고,
   폴더 **밖** `apply_patch` 는 카드가 떴다. 즉 엔진 간 동작이 지금도 다르다(claude 는 둘 다 묻는다).
3. **직급별** — 사용자가 말한 결대로 "부장은 묻고 아래는 자동" 도 가능하지만, **안전과 직급은 무관하다**
   (D-32 가 셸 허가를 직급에서 뗀 이유가 그것이다). 직급으로 가르는 건 권하지 않는다 — 번거로움의
   원인은 직급이 아니라 **머릿수** 다.
4. **되돌릴 수 있는가** — git 추적 파일 수정은 복구 가능, `rm -rf` 는 아니다. 좋은 기준이지만 판정이 비싸다.

필요한 것(어느 설계든):
- **보이는 기록.** 자동 허가된 것은 사무실 로그·터미널에 남아야 한다 — 안 그러면 "뭐가 내 허락 없이
  실행됐는지" 를 알 수 없다. 지금 통합 테스트가 쓰는 `auto-approve` 로그 줄이 참고가 된다.
- **끄는 길.** 설정에 "전부 묻기" 모드. 처음 쓰는 폴더나 민감한 작업에서 되돌릴 수 있어야 한다.

## U-04 · 2026-10-08 · 보고하러 온 캐릭터가 종종 클릭이 안 된다

### 증상

보고하러 **내 책상 쪽으로 온 AI** 를 클릭하는데 **종종** 안 눌린다. 늘 그런 건 아니다.

### 짚이는 자리 (코드 근거, 실기 확인은 안 함)

판정 자체는 제대로 설계돼 있다 — `office_view.dart` 머리말이 *"탭 → OfficeLayout.hitTest(**지금 위치
기준**)"* 이고, 실제로 애니메이션된 현재 위치를 넘긴다:
`layout.hitTest(local, scene, _motion.placementsAt(_now), _scroll)`.

그런데 `hitTest`(`office_layout.dart:488`)는 멤버마다 **어느 좌표계로 볼지**를 고르는데, 그 기준이
애니메이션 상태가 아니라 **목표 상태 플래그**다:

```dart
bool drawsInBar(SceneMember m) => m.isQueued && m.queueIndex! < myDeskSlots;   // :460

// 1. 바(슬롯)에 그려진 대기자 — 뷰포트 좌표 그대로.
for (...) { if (!drawsInBar(scene.members[i])) continue; if ((ps[i].center - p).distance <= r) ... }
...
// 2. 스크롤 영역 — 콘텐츠 좌표로.
final c = toContent(p, scrollOffset);
for (...) { if (drawsInBar(scene.members[i])) continue;  if ((ps[i].center - c).distance <= r) ... }
```

**용의자 ① — 걸어가는 동안 좌표계가 어긋난다. ← 가장 유력**

멤버가 줄에 서기로 **정해지는 순간** `isQueued`·`queueIndex` 가 생겨 `drawsInBar` 가 **true** 가 된다.
그때부터 `hitTest` 는 그 멤버를 **뷰포트 좌표**로 판정한다. 그런데 화면에는 아직 **자기 책상에서
걸어오는 중**이라 스크롤 영역에 그려진다. 즉 **그리는 좌표계(콘텐츠)와 판정 좌표계(뷰포트)가 다르다** —
어긋나는 양이 정확히 `scrollOffset` 이다.

→ 그래서 **사무실을 스크롤하지 않았을 때는 (offset 0 이라) 멀쩡하고, 스크롤한 상태에서 걸어오는 중에만
빗나간다.** "종종" 과 맞는다.

**용의자 ② — 바 영역의 빈 슬롯이 클릭을 삼킨다**

```dart
final k = slotAt(p);
if (k != null) {
  final q = scene.queue;
  if (k < q.length) return q[k].memberId;
  if (k == myDeskSlots - 1 && q.length > myDeskSlots) return q[myDeskSlots - 1].memberId;
  return null;          // ← 슬롯 영역인데 그 슬롯이 비면 여기서 끝. 아래 캐릭터 검사로 안 내려간다
}
```

바 영역 안인데 그 슬롯이 아직 안 찼으면(걸어오는 중이라 `scene.queue` 에 아직 없을 수 있다)
**거기 캐릭터가 그려져 있어도 `null`** 이 된다. 슬롯은 4개(`mySlotCount = 4`)다.

**참고**: 클릭 반경은 `max(18, charRadius + 4)` 로 최소 18px 는 보장돼 있다(패스 6) — 너무 작아서는
아닐 가능성이 높다.

### 가를 수 있는 시험 (사용자가 해 볼 수 있는 것)

1. **사무실을 맨 위로 스크롤한 상태**에서만 클릭해 본다 → 안 틀리면 ①이 맞다.
2. 캐릭터가 **다 걸어와 줄에 선 뒤**에 클릭해 본다 → 그때는 되면 역시 ①(또는 ②)이다.
3. 줄이 **5명 이상**일 때 유독 그런지 본다(슬롯 4개를 넘으면 마지막 슬롯이 겹친다).

### 후보 수정

- **①**: `hitTest` 가 좌표계를 고르는 기준을 **목표 상태(`drawsInBar`)가 아니라 지금 그려지는 위치**로
  바꾼다. 그리는 쪽(`placementsAt`)과 판정하는 쪽이 **같은 한 곳**에서 좌표계를 정하게 만드는 것이 근본
  수정이다 — 지금은 둘이 따로 판단해서 어긋날 수 있다.
- **②**: 슬롯이 비었으면 `return null` 하지 말고 **아래 캐릭터 검사로 내려가게** 한다.

둘 다 `office_layout.dart` 한 함수 안의 일이라 범위는 작다. 단위 테스트로 재현할 수 있을 것이다
(스크롤 오프셋을 준 채 "걸어오는 중" 배치를 만들어 `hitTest` 가 그 멤버를 돌려주는지).

### 상태

**고침 — 2026-10-11, T52** (커밋 `ddd324f`). **위의 용의자 ①·② 는 둘 다 아니었다.**

- **진짜 원인**: 그리는 쪽과 누르는 쪽이 "바(뷰포트 좌표)에 있는 캐릭터" 를 **다르게 판단했다.** 페인터(`office_painter.dart` `_inBar`)는 슬롯 대기자 **와 보고 방문자** 를 바에 그리는데, `hitTest` 는 슬롯 대기자만 바로 쳤다. 그래서 내 책상 옆에 도착한 보고 방문자는 `hitTest` 에서 "바의 빈 곳" 으로 떨어져 **한 번도 눌린 적이 없다.** 걸어오는 중(스크롤 영역 위를 지날 때)에만 눌려서 "종종" 으로 보였다.
- 용의자 ①("걸어오는 동안 좌표계가 어긋난다")이 틀린 이유: 페인터도 **같은 플래그**(`drawsInBar`)를 본다 — 줄에 서는 멤버는 그리는 쪽도 누르는 쪽도 같이 바뀐다. 어긋나는 것은 그 플래그가 **없는** 보고 방문자였다. 시험 1(스크롤 맨 위)을 해 봤어도 안 눌렸을 것이다.
- **고친 것**: 판단을 `OfficeLayout.drawsInBar(m, visiting:)` 한 곳으로 모으고 페인터와 `hitTest` 가 **같은 방문 집합**을 받는다.
- **같이 나온 것**: 페인터는 방문 여부를 `bubbleOverrides` 에 있는지로 봤는데, 거기에는 자리에 앉은 채 뜨는 **"복구" 말풍선**도 들어 있었다. 그 멤버를 3초 동안 바 좌표로 그리고 있었다(스크롤 0 이면 안 보이는 버그). 방문 집합(`visitingIds`)으로 바꿨다.
- **남은 것(모양만)**: 사무실을 스크롤한 상태에서 캐릭터가 자리 ↔ 바를 오갈 때, 좌표계가 바뀌는 순간 스크롤 양만큼 튀어 보인다. 클릭은 그려진 자리에서 맞는다. 고치려면 이동 모델이 스크롤을 알아야 한다 — 이번에는 안 했다.
- **확인**: 위젯 테스트(`movement_test.dart` — 보고하러 온 캐릭터를 걸어오는 중·도착 후에 탭) + 단위(스크롤 0·120 둘 다). 실제 창에서는 아직 못 봤다.

## U-05 · 2026-10-11 · 동작 중인 AI 의 세부 모델을 알 수 없다 — 엔진만 보인다

성격: **버그가 아니라 UX 결함**(표시 누락). 사용자 표현 그대로 "이것도 수정했으면 해".

### 증상

동작 중인 멤버를 클릭하면 패널 헤더에 **엔진(`Claude` / `Codex`)** 은 나오는데, 그 세션이 실제로 쓰는
**세부 모델**(Opus 5 인지 Fable 5.1 인지, gpt-6-astra 인지 sol 인지)은 어디에도 없다. 같은 "Claude" 배지를
달고 있어도 비용·속도·능력이 전혀 다른데 구분이 안 된다.

### 재현

1. 멤버를 아무나 클릭 → 오른쪽 패널 헤더.
2. 이름 옆 배지에 `claude` 또는 `codex` 만 있다. 그 아래 트리 줄·cwd 줄·사용량 줄에도 모델명이 없다.
3. 사무실 뷰의 배지·툴팁도 같다(`engineLabel` = `Claude`/`Codex` 둘뿐).

### 짚이는 자리 (코드 읽은 추정 — 고칠 때 다시 볼 것)

**1) 모델명을 들고 있는 필드가 아예 없다.** 데몬 `Member`(`dev/daemon/src/office/types.ts:87` 등)와 앱
`Member`(`dev/app/lib/model/member.dart:131`) 모두 `engine` 만 있고 모델 필드가 없다. 표시하는 쪽
(`dev/app/lib/panel/right_panel.dart:357` 의 `_Badge(member.engine.name)`,
`dev/app/lib/office/office_scene.dart:302` 의 `engineLabel`)은 그래서 엔진밖에 못 쓴다.

**2) 우리가 모델을 지정하지도 않는다.** 데몬 전체에 `--model` 인자가 **없다**(`grep '--model' dev/daemon/src`
→ 0건). 즉 모델은 각 CLI 의 기본값이고, 알아내려면 **CLI 에게서 읽어야** 한다.

**3) 그런데 읽을 자료는 이미 들어오고 있다.** ← 여기가 핵심

- **Claude**: statusLine 페이로드에 `model: { id, display_name }` 가 **매번** 온다. 실측 픽스처
  `dev/daemon/test/fixtures/usage/claude-statusline-fresh.json` 에 `"display_name": "Opus 5 (1M context)"`,
  `"id": "claude-opus-5[1m]"` 가 그대로 있다. 받는 자리도 멤버 단위로 이미 열려 있다 —
  `dev/daemon/src/office/Office.ts:2622` 의 `receiver.on('status-line')` 는 `memberToken` 으로 멤버를
  찾아 `usage.applyStatusLine({ id, engine }, payload)` 에 넘긴다. **파서가 `model` 만 안 꺼낸다**
  (`dev/daemon/src/usage/parse/claudeStatusLine.ts` 의 `ClaudeStatusLineInfo` 에 필드가 없다).
  덧붙여 **모든 hook 페이로드에도 `model?: string` 이 있다**(`dev/daemon/src/hooks/types.ts:54`) —
  Claude 쪽은 채널이 둘이다.
- **Codex**: statusLine 이란 게 없다(Office.ts:1983 주석). 대신 세션 헤더에 한 줄 나온다 —
  `dev/spike-1/out/codex-screen-00-ready.txt:13` 의 `│ model:     gpt-6-astra high   /model to change`.
  `/status` 화면에도 같은 줄이 있다(`codex-full-01-status-before-turn.txt:12`).
  즉 **화면에서 긁어야** 하고, 자리는 `tui-maps/codex-*.json` 이다(이미 `^\s*│ model:\s+loading\b` 를
  promptReady 의 `noneOf` 로 쓰고 있으니 패턴 자리도 잡혀 있다).

**함정 세 개**(미리 적어 둔다):

- 모델은 **세션 중에 바뀔 수 있다**. Codex 는 사용량 한도에서 `model-switch-offer` 가 뜨고
  (`tui-maps/codex-0.154.json:56`), 두 CLI 다 사용자가 `/model` 로 바꿀 수 있다. → **생성 시점 설정이
  아니라 "지금 쓰는 모델" 을 살아 있는 값으로 들고 있어야** 한다.
- Codex `resume` 직후에는 헤더가 복원된 대화에 밀려 **안 보일 수 있다**(`InputQueue.ts:370` 주석이
  같은 현상을 적어 두었다). → 헤더를 한 번만 긁고 기억하되, 못 긁었으면 "모름" 으로 두고 나중에
  `/status` 로 보강.
- Claude `display_name` 은 `"Opus 5 (1M context)"` 처럼 **꾸밈이 붙는다**. 배지에 넣을 짧은 이름
  (`Opus 5`)과 원문을 분리해 두는 게 낫다.

### 후보 수정

1. **데몬**: `claudeStatusLine.ts` 에 `model: { id, displayName }` 추출 추가(순수 함수라 테스트 쉽다)
   → 멤버 런타임에 `currentModel` 로 저장 → 바뀌면 멤버 갱신 알림. Codex 는 `tui-maps` 에 `model` 캡처
   패턴을 넣고 화면 파싱으로 같은 필드를 채운다.
2. **와이어**: `SnapshotMember` 에 `model?: { id?, label }` 추가(없으면 "모름" — 구버전/Codex 미확인과
   같은 취급).
3. **앱**: `Member` 에 같은 필드 → 패널 헤더 배지를 `claude` 에서 `claude · Opus 5` 로. 사무실 배지는
   좁으니 **툴팁에만** 넣는 쪽이 안전하다(`office_painter.dart:835` 가 이미
   `'$deskTooltip · $engineLabel'` 을 만든다 — 여기 한 줄).
4. 모델을 모르면 **빈칸이 아니라 생략**(배지가 흔들리지 않게).

범위: 데몬 파서 1 + 맵 1 + 와이어 1 + 앱 표시 2~3곳. 기능 자체는 작지만 **엔진 2종의 출처가 전혀 달라서**
(이벤트 vs 화면 긁기) Codex 쪽이 일의 대부분이다.

### 관련 — 아직 문서에 없던 요청: 부장의 세부 모델 **선택**

2026-10-10 에 말로만 나눈 요청이 이것과 같은 배관을 쓴다. 잊지 않게 여기 같이 적어 둔다:

- 부서를 만들 때 부장의 **세부 모델을 지정**할 수 있으면 좋겠다(예: Claude Fable 5.1, Codex gpt-6-astra).
- **기본값은 각 LLM 의 최상위 모델**.
- 생성 폼에 **"세부설정"** 항목(접는 영역)을 만들어 그 안에서 고른다 — 기본 화면은 지금처럼 단순하게.
- 사용자 요청: **"일단 지금 실 사용 중이라 바로 적용시키진 말아줘."**

U-05(읽어서 **보여 주기**)와 이 요청(**정해서 넘기기**, `--model` 인자 추가)은 **같은 필드의 양쪽**이다.
→ 한 번에 할 때 **U-05 를 먼저** 하는 게 낫다: 표시가 되면 선택이 실제로 먹었는지 눈으로 확인된다.

### 상태

**고침 — 2026-10-11, T52** (커밋 `f20ce08`). **"Codex 는 화면에서 긁어야 한다" 는 틀렸다** — 훨씬 쉬운 길이 있었다.

- **Codex**: **모든 hook 페이로드에 `model`(id)이 실려 온다**(spike-1 의 실측 hookLog 5건 전부 `gpt-6-astra`). 화면·tui-map 을 건드릴 필요가 없다. 위에 적은 "resume 직후 헤더가 밀려 안 보인다" 함정도 해당 없음.
- **Claude**: statusLine 의 `model{id, display_name}` + `SessionStart` hook 의 `model`(id). 실측: 출근 0.8초 만에 id(`claude-opus-5-5`)가 먼저 오고, 첫 턴 뒤 표시 이름(`Opus 5.5`)으로 바뀐다.
- **어디에 실었나**: 멤버 필드를 새로 만들지 않고 **`MemberUsage.model{id,label}`** 에 넣었다 — 멤버 단위·영속·알림(`usage.member`) 채널이 이미 있고 스키마를 안 건드린다.
- **앱**: 패널 헤더의 엔진 배지 옆에 짧은 이름(`claude` `Opus 5.5`), 툴팁에 전체(`Opus 5 (1M context) · claude-opus-5[1m]`). 끝의 괄호 꾸밈만 뗀다. 아직 못 봤으면 배지를 그리지 않는다. 책상 시맨틱 라벨·콘솔 `usage` 에도 붙는다.
- **세션 중에 바뀌면 따라 바뀐다**(`/model`, Codex 의 모델 전환). id 만 아는 hook 이 statusLine 의 좋은 이름을 되돌리지 않는다.
- **확인**: 단위 + 진짜 claude(`autoapproval.integration.test.ts` 가 모델이 사용량에 실리는 것까지 본다). **Codex 는 실기로 못 돌렸다** — 근거는 실측 hookLog 픽스처다.
- **세부 모델 선택**(위 "관련" 절)은 **아직 안 했다.** 표시가 먼저 들어갔으니 이제 선택(`--model` 넘기기)이 먹었는지 눈으로 확인할 수 있다. "세부 설정" 접는 영역은 U-02 가 만들어 뒀다 — 거기에 얹으면 된다.

## U-06 · 2026-10-11 · Codex 멤버는 세부 모델이 안 보인다 — 첫 일을 받기 전까지

U-05(T52)를 넣고 사용자가 새 빌드에서 확인하다 발견. 사용자 말: *"claude 는 세부 모델이 보이는데 codex 는 안 보인다."*
사용자 지시: **지시하기 전에는 기록만.** 코드는 건드리지 않았다.

### 증상

멤버를 클릭하면 Claude 멤버는 엔진 배지 옆에 모델(`Opus 5.5`)이 뜨는데, Codex 멤버는 `codex` 배지뿐이다.

### 관찰 (실기 — 데몬을 다시 띄운 직후 콘솔 `usage`, 읽기만 했다)

```
반론담당   [codex · gpt-5.6-sol]  …  2026-10-11T09:24:52Z    ← 재기동 뒤 일(task#30)을 받았다
디자인팀장 [codex]                …  2026-10-08T12:11:44Z    ← 재기동 뒤 한 번도 안 움직였다(갱신 시각이 사흘 전)
기획팀장   [claude · Opus 5.5]    …
부장       [claude · Opus 5.5]    …
```

즉 **Codex 도 모델은 들어온다 — 단, 그 멤버가 일을 한 번 받은 뒤에.** 같은 Codex 인데 일을 받은 반론담당은 보이고,
가만히 있는 디자인팀장은 안 보인다. "Codex 는 안 된다" 가 아니라 **"Codex 는 늦다"** 다.

### 짚이는 자리 (추정 — 고칠 때 다시 볼 것)

U-05 는 모델을 이렇게 읽는다: Claude 는 **statusLine**(화면을 그릴 때마다 — 출근 직후 바로 온다), Codex 는
**hook 페이로드의 `model`**. Codex 에는 statusLine 이 없으니 **hook 이 한 번 와야** 안다.

- 그런데 `resume` 으로 되살아난 Codex 세션은 **일을 받기 전까지 hook 을 하나도 안 보내는 것으로 보인다**
  (디자인팀장의 사용량 갱신 시각이 재기동 이후로 안 바뀐 것이 근거). spike-1 의 실측 hookLog 에는 `SessionStart`
  에 `model` 이 있었지만 그건 **새로 띄운** 세션이었다 — resume 에서도 `SessionStart` 가 오는지는 **확인 안 함.**
- 새로 고용한 Codex 멤버(resume 아님)는 `SessionStart` 때 바로 뜰 가능성이 있다 — **확인 안 함.**
  사용자가 본 멤버가 어느 쪽이었는지에 따라 범위가 달라진다.
- 그리고 `MemberUsage.model` 은 DB 에 남으므로(U-05), 한 번 본 뒤로는 재기동해도 보인다. 이번에 안 보인 것은
  **U-05 가 들어간 뒤 그 멤버가 아직 한 번도 hook 을 안 보냈기** 때문이다(옛 행에는 `model` 이 없다).
  → 시간이 지나 모든 멤버가 한 번씩 일하면 이 증상은 **저절로 줄어든다.** 다만 새 Codex 멤버·모델을 바꾼 직후에는 다시 난다.

### 후보 수정

1. **화면 헤더에서 읽는다** — Codex 는 시작할 때 `│ model:  gpt-6-astra high  /model to change` 를 찍는다
   (`dev/spike-1/out/codex-screen-00-ready.txt:13`). U-05 문서가 처음에 적었다가 "hook 이 있으니 필요 없다" 고 접은
   길이다. 출근 직후에 바로 알 수 있지만, resume 직후에는 복원된 대화에 밀려 **안 보일 수 있다**(`InputQueue.ts:370` 주석).
2. **기록 파일(rollout)에서 읽는다** — Codex rollout JSONL 에 세션 메타가 있으면 거기서 모델을 꺼낸다.
   resume 에서도 통하고 화면에 기대지 않는다. rollout 에 모델이 실리는지는 **확인 안 함**(지금 파서는 `token_count` 만 본다).
3. **확인용 세션의 `/status` 를 빌린다** — 이미 5분마다 `/status` 화면을 읽고 있고 거기에도 `model:` 줄이 있다.
   다만 그건 **멤버의 모델이 아니라 기본 모델**이다 — 멤버가 `/model` 로 바꿨으면 틀린다. "기본값" 이라고 흐리게 보여 주는 정도.
4. **그대로 둔다** — 첫 일 뒤에는 뜨고, 한 번 뜨면 남는다. 가장 싸지만 "방금 고용한 Codex 가 뭘로 도는지" 를 못 본다.

### 상태

미해결. 기록만 했다(사용자 지시). 고치기 전에 가를 것: **새로 고용한 Codex 는 바로 뜨는가**(resume 만의 문제인가).

## U-07 · 2026-10-11 · Codex 멤버의 터미널 탭은 스크롤이 안 된다 — Claude 만 고쳐졌다

코덱스 꺼는 작업 아예 안 한 거 아니냐?"* 사용자 지시: **지시하기 전에는 기록만.** 코드는 건드리지 않았다.

### 증상

Claude 멤버의 터미널 탭은 휠·트랙패드로 대화가 위로 넘어간다(U-03 이 고친 것). **Codex 멤버의 터미널 탭은 여전히 안 넘어간다.**

### T52 가 Codex 에 대해 한 것과 안 한 것 (있는 그대로)

| | Codex 쪽 | 근거 |
|---|---|---|
| U-03 터미널 스크롤 | **확인 안 함.** 고친 코드(휠 번호 · `?1006h`)는 엔진을 가리지 않지만, 시험은 claude 로만 했다. 그러고는 "Codex 는 인라인 렌더라 원래 된다" 고 **확인 없이 적었다 — 틀렸다** | 이 항목 |
| U-05 모델 표시 | 구현은 했다. 근거는 **옛 실측 픽스처**(spike-1 hookLog)였고 실기는 안 돌렸다 → 늦게 뜨는 문제를 놓쳤다 | U-06 |
| U-02 허가 방식 | `apply_patch` 판정을 넣었지만 **단위 테스트뿐**이다. 실기는 claude 로만 돌렸다 | 미확인 |
| U-01 · U-04 | 엔진과 무관한 앱·데몬 공통 코드 | — |

worklog 에 "Codex 실기는 못 돌림" 이라고는 적었다. 그러나 U-03 에서는 **모른다고 적어야 할 자리에 "원래 된다" 고 단정했다.**
그 한 줄 때문에 Codex 터미널을 볼 생각을 안 했다.

### 관찰 (실기 — codex 를 pty 로 띄워 모드만 읽었다. 프롬프트는 안 보냈다)

codex-cli **0.159.0**:

```
RAW modes      : ?2004h ?1004h ?2026h ?25l ?1049h ?1007l ?1000h ?1002h ?1003h ?1006h ?25h ?2026l
SERIALIZE modes: ?1049h ?2004h ?1004h ?1003h ?1006h
기타 시퀀스     : ESC[>4;0m   ESC[>7u
```

- **`?1049h` — Codex 도 전체 화면(alt 버퍼)이다.** "인라인 렌더" 는 옛 버전(0.154) 이야기였다(`tui-maps/README.md` 의 그 문장도 낡았다).
  alt 버퍼라 터미널 쪽 스크롤백은 없다 — Claude 와 같은 처지다.
- 마우스 추적(`?1000h ?1002h ?1003h`)과 SGR 인코딩(`?1006h`)을 켠다 → **앱은 Codex 에도 휠을 `ESC[<64;x;yM` 로 보내고 있을 것이다**(Claude 와 같은 경로).
- Claude 에 없던 것 셋: **`?1007l`**(alternate scroll 끔 — 휠을 화살표로 바꿔 보내지 말라는 뜻), **`ESC[>7u`**(kitty 키보드 프로토콜), **`ESC[>4;0m`**(modifyOtherKeys).

### 짚이는 자리 (전부 추정 — 하나도 확인 안 함)

보낸 휠을 **Codex 가 받고도 안 넘기는지, 아예 못 받는지**를 모른다. 갈래:

1. **Codex 가 휠로는 대화를 안 넘긴다.** 마우스를 켜는 것과 휠에 스크롤을 붙이는 것은 다른 일이다. 넘기는 길이 키(PgUp/PgDn ·
   Ctrl+T 기록 보기 같은 것)뿐일 수 있다. 그러면 앱이 할 일은 "휠 → 그 키" 로 바꿔 보내는 것이다.
2. **휠은 받는데 모양이 다르다.** Claude 가 버튼 68 을 무시했듯, Codex 가 기대하는 보고 모양이 따로 있을 수 있다.
3. **`ESC[>7u`(kitty 키보드)를 앱 터미널이 모른다.** xterm 패키지가 이 요청에 답하지 못해 입력 해석이 어긋날 수 있다 — 휠보다는 키 쪽 문제일 가능성이 높지만 적어 둔다.
4. **데몬이 중간에서 먹는다.** `member.type` 으로 들어온 데이터를 Codex 세션에서 다르게 다루는 곳(입력 큐의 "사용자 타이핑" 판정 등)이 있는지 **안 봤다.**

### 가르는 방법 (고치기 전에 할 것)

U-03 때 claude 에 한 것과 **똑같이** 한다: codex 를 pty 로 띄워 대화를 세 화면쯤 쌓고, `ESC[<64;x;yM` · 옛 인코딩 · PgUp 을
직접 써넣어 화면이 바뀌는지 본다. 그러면 1 · 2 가 갈린다. 대화를 쌓으려면 턴을 몇 번 써야 한다(사용량).
그다음 실제 앱의 Codex 터미널 탭에서 무엇이 나가는지(`member.type` 페이로드)를 본다 → 3 · 4.

### 상태

**고침 — 2026-10-11, T53.** 위의 갈래 넷 중 **어느 것도 아니었다** — 이번에는 추정으로 고르지 않고 실기로 좁혔다.

- **Codex 자체는 멀쩡했다.** pty 로 띄워 직접 넣어 보니 SGR 휠 · 옛 인코딩 휠 · 버튼 68 · PgUp/PgDn · Shift+↑ 가 전부 대화를 넘긴다. 데몬을 거쳐도(`member.type`), 데몬을 재기동해 resume 된 세션에서도 넘어간다.
- **앱이 내보내는 것도 겉보기엔 멀쩡했다.** codex 의 실제 화면을 앱 터미널 위젯에 흘려 넣고 휠을 굴리면 `ESC[<64;x;yM` 이 나간다.
- **남은 차이는 좌표였다.** 위 실험은 전부 **대화 영역 한가운데**(20,10)에 대고 했다. 위치를 바꿔 보니:

  ```
  O 휠업 @ (열 20, 행 10)    LINE-50…70 → LINE-32…54
  O 휠업 @ (열 100, 행 10)
  x 휠업 @ (열 20, 행 1)
  O 휠업 @ (열 20, 행 24)
  x 휠업 @ (열 20, 행 25 ~ 30)     ← 입력창 · 상태줄
  ```

  **Codex 는 포인터가 대화 영역 위에 있을 때만 휠로 대화를 넘긴다.** Claude 는 위치를 안 본다.
- **진짜 원인**: xterm 패키지(4.0.0)의 스크롤 처리기가 휠 위치를 `event.position`(**창 전체 기준** 좌표)으로 칸을 계산한다(`scroll_handler.dart` — `getCellOffset` 은 뷰 기준 좌표를 기대한다). 터미널 탭은 창의 오른쪽 아래에 있으니 **행은 늘 맨 아래로 잘린다** → Codex 에게는 입력창에 대고 굴린 휠이다. 트랙패드는 더 나빴다 — 위치를 한 번도 갱신하지 않아 **늘 (1,1)** 로 나갔다(그 행도 Codex 가 무시한다).
- **고친 것**(앱만): 터미널 탭이 포인터 위치를 뷰 기준 칸으로 직접 계산해 적어 두고(`terminal_tab.dart` `_trackPointer`), 휠 처리기가 패키지가 준 위치 대신 그걸 쓴다(`terminal_cache.dart` `StandardWheelMouseHandler.pointerCell`). 휠 · 트랙패드 둘 다.
- **U-03 과의 관계**: U-03 은 휠 **번호**(68 → 64)를 고쳤고 그게 Claude 를 살렸다. Codex 는 번호는 원래 상관없었고(68 도 받는다) **위치**가 문제였다. 한 패키지의 스크롤 처리기에 버그가 둘 있었고 엔진마다 다른 쪽에 걸렸다.
- **쓰는 사람이 알 것**: Codex 터미널에서는 포인터를 **대화가 보이는 영역**에 두고 굴려야 한다(입력창 위에서는 안 넘어간다 — Codex 의 동작이다).
- **확인**: 위젯 테스트(창 안에서 밀려 있는 터미널 · 휠과 트랙패드 — 고치기 전 코드로 돌리면 `36;10` · `1;1` 이 나가며 실패한다) + **진짜 codex** `codexscroll.integration.test.ts`(바닥 행 · (1,1) 은 무시, 대화 영역은 넘어감). **실제 앱 창에서는 아직 못 봤다.**
- **U-06(모델이 늦게 뜬다)은 그대로 미해결**이다 — 이번에 지시받은 것은 스크롤뿐이다. U-02 의 Codex 쪽(`apply_patch`)도 여전히 실기 전이다.
